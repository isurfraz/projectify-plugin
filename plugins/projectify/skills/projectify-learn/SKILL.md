# Learn into Projectify

The person wants something explained, or turned into a workflow their team and Claude can run again and again: any kind of work, from a weekly report or a hire to a release, a recipe or an ad. You read it here, on their computer, more thoroughly than a server can: every word, and for a video the speech, every scene and the text on screen. Projectify shows the explainer filling in as you go.

## Start
1. Call `learn` with the source ({kind, name, path or url}) and the goal (explain, or workflow when they said so). If they gave you an explainer ref (EX-4) from Projectify, fill that one in instead: `get_explainer` and carry on from its stages.
2. The answer has the upload command and the shapes to write. Keep it open.

## Read it
1. Read it where it is, the way its kind needs (SPM-823): a video or a recording on this computer or at a link: run the Projectify reader (`python3 analyse_media.py <file or link> --out <folder>`; get it with `curl -fsSL <api>/v1/public/learn/analyse_media.py -o analyse_media.py` if the projectify-learn skill did not bring it), which writes the transcript, scene frames, contact sheets and text read off each frame. A web page: read the page itself. A document: read all of it, headings and tables included. Pictures: look at each. Pasted text: read it as given.
2. For a video, look properly: open every contact sheet, then the frames that show settings, menus, prompts or results, lined up with the transcript by time. For any source, note what it says and what it only shows or assumes.
3. Write down the process (what always happens, in order) apart from the techniques (tricks that apply only in some cases, each with when to use it), and its outline: what it delivers and to whom, what starts it, what a run takes in, who takes part, the decisions and their rules, the checks and their criteria, and any template quoted word for word.
4. For a video, upload only the frames you will use (about 640 px wide JPEGs) with the upload command, and refer to them by frame id. Other sources need no frames.

The reader is bundled with this skill: `python3 "${CLAUDE_PLUGIN_ROOT}/skills/projectify-learn/analyse_media.py" <file or link> --out <folder>`. Without the plugin, download it: `curl -fsSL https://api.projectify.si/v1/public/learn/analyse_media.py -o analyse_media.py`. It needs python3 and ffmpeg; whisper.cpp (or mlx-whisper, openai-whisper, faster-whisper, or OPENAI_API_KEY), yt-dlp and tesseract make it better, and it says how to add each one missing. Tell the person what is missing in one line and carry on with what there is.

## Write it
- **digest** (update_explainer digest): title, kind (how_to | concept | story | reference | mixed), tldr (two sentences), audience, minutes {source, read}, ideas [{title, body, at}], steps [{title, body, app, settings [{name, value}], at, to, frames ["f12"]}], tools [{name, what, cost}], terms [{term, means}], tips [{text, kind tip|trap, at}], numbers [{label, value, at}], techniques [{name, summary, useWhen [..], avoidWhen, steps, snippet, settings, worksWith, tags, examples, source {at, to}}], unclear [..]. `at` is seconds into the video.
- **explanation** (update_explainer explanation): plan (what they will learn, in order) and blocks, each {type, title, ...}: tldr {text} · text {body} · diagram {style flow|cycle|tree|compare, nodes [{id, label, note}], edges [{from, to, label}], caption} · cards {cards [{title, body, at}]} · steps {steps [{title, body, at, frames}]} · table {columns, rows, note} · techniques {names} · tips {tips [{text, kind, at}]} · picture {frame | file | url, caption, prompt} · quote {text, who, at} · glossary {terms} · quiz {questions [{q, options, answer, why}]}. Lead with the tldr and a diagram of the whole process; give the steps their frames; show the techniques apart; end with three quiz questions.
- **workflow** (save_workflow): title, summary, useWhen (what a person would say), graph {nodes, edges}. Node kinds: phase (a group of steps, once or for each item); input (something to bring when it starts); step (something a person or claude does); prompt (ask an ai model, with blanks filled from the run); tool (use an app or a connector); decision (go one way or another); check (someone looks before it goes on); output (what the run hands over, and where); note (a note for people reading it); flow (run a workflow you already have). A node: id, kind, title, summary, body, phase (a phase node's id), actor person|agent|either, app, url, settings [{name, value, why}], prompt {text with {{blanks}}, model, fills [{key, label, example}]}, fields (on an input: [{key, label, type text|long_text|image|file|link|choice|number, required, options, hint}]), produces [..] (a list of names), techniques [{technique (its name), use always|auto|never, note}], tips, traps, cost, time, connector {server, tool, args} (an MCP tool that can do a tool step), source {at, to, quote}, media [{frame}]. A phase may repeat: repeat {over: an input key with one item per line, as: the blank each item fills, label, together}. Edges: {from, to, label, kind next|yes|no|retry}. Also (SPM-818, SPM-823): instructions (Markdown for Claude), doneWhen [..], role, deliver {to doc|task|file|link|message|none, where, title} on an output, needs {what, suggested [{model, app, why}]}, costs [{amount, unit, per step|item|hour|second|take, count}], onlyIf {input, is given|empty|<value>} or {text}, perVariation, a field's variation, a fill's from. The digest also takes outline {outcome, deliverTo, trigger, cadence, inputs [{name, kind, required, note}], roles [{name, does}], decisions [{question, rule, ways [..]}], checks [{what, who, criteria [..]}], templates [{name, text}]}; a technique's avoidWhen is a list, like useWhen.
- **make it reusable**: Build it from the outline: inputs become one input node, roles become actors, decisions become decision nodes, checks become check nodes, the outcome becomes the output node with deliver {to: doc|task|file|link|message|none, where, title}, and templates go into the steps that use them word for word. Phases only when the process has stages (none for five or six steps). Each step a person or Claude does gets doneWhen (two to four checkable lines); each step Claude does gets instructions (short Markdown with {{blanks}}); a person step names its role when the source does. actor by what the step is: a person or role for physical, relational, legal or taste work; Claude for research, drafting, data and tool work; either where both can. Prompt nodes only where an AI model is really prompted. A workflow must work for the next run, not only the source's example: what the source happened to have becomes an optional input, and the steps that use it get onlyIf {input, is: "given"} (with the other way for "empty"); a step that depends on the brief in a way no input captures gets onlyIf {text}. A step that relies on a particular tool, app, model or service says what it needs (needs.what) and what suits it (needs.suggested, each with why); never lock one. Costs [{amount, unit, per: step|item|hour|second|take, count}] only where a step really costs something and the source says how much. Add the steps the result needs that the source skipped or did by hand (gathering what later steps need, a draft before an expensive step); every part the result has gets a step that makes it, with the tool that does it reliably. Inputs that are natural alternatives (copy lines, tracks, languages, audiences) are fields with variation: true, one per line; only the steps that differ per alternative are perVariation. A repeating phase whose items do not depend on each other sets repeat.together. Steps that all happen after one step are plain arrows from it (they run one after another, then join); a decision has labelled arrows and its rule in instructions. Every prompt fill says where it comes from: an input key, "item", or a step id.
- **checks**: a check node has gate {who person|agent|both|either, mode pass|pick, shows, showsNode, criteria [{text, must}], failIf, methods (ways Claude may check: Open the file itself, Read every word, Compare with the inputs and the brief, Check the numbers add up…), banned (Judge from the prompt alone, Trust the app’s own preview…), steps, onFail retry|ask|stop, backTo (a node id), tries}. Put a check wherever the source stops to look at a result (a person watching a draft is who: person). Use pick where someone chooses from several (faces, takes). Every retry needs a backTo or a retry arrow.

Set each stage as you go (`update_explainer` stage {key, state, detail}): read, understand, explain, workflow. A failure is a stage set to failed with the reason in one line and the fixes that fit; then tell the person and stop guessing.

## Several sources: a playbook (D-127)
- A playbook is a guide to one area of work: which workflow or technique to use when, what always holds, the tools and the words. It points to workflows and techniques and never copies them.
- "Learn from these videos" with two or more sources: call `learn` with `sources` [..] and `playbook` {mode, focus}. mode: playbook (every distinct workflow and technique, repeats merged; the default), best (one best workflow) or each (one workflow per source). The answer lists each source with its explainer and says how to read, combine and save. "Build playbook PB-3" or "read the sources of PB-3": `get_playbook` with build: true gives the same.
- Read every source that is not understood yet and write its digest (`update_explainer`; no explanation is needed). Then combine: take each source on its own first, merge only what is the same thing, and never average a disagreement away: record it in `conflicts` with every way, its sources, the one you chose and why (a trusted source wins, else most sources). Keep which sources each step and technique came from.
- Save: `save_technique` once per technique (reuse one the Library has), `save_workflow` per workflow, then `save_playbook` (through `act`) with the guide, add_items, conflicts and done: true. It is a draft until the person presses Mark ready.
- "Using the X playbook, make…": `get_playbook` first. Pick from its "Which to use", tell the person which you picked and why, then `run_workflow` with `playbook` (what always holds then comes with every step) or `get_technique`. If nothing in it fits, say so and ask; do not improvise a process the playbook does not have.

## Run and change workflows
- "Do the weekly client report": `list_workflows` with q (through `act`), then `run_workflow`. Projectify drives the run: each answer gives the goal, the brief, what earlier steps made, the step's instructions and when it is done. Do what it says, report with `update_run` (only the step the run is at; a check with state "review"), and carry on with other runs while a check waits on the person in Approvals. The output step hands the result over (a doc or task is written for you); the person is told when the run is done.
- "Make a copy where every check is Claude-only": `get_flow` (raw: true), change the graph as asked, then `duplicate_workflow` with the new graph and a note (through `act`). "Remove the steps between X and Y" on the workflow itself: `save_workflow` with workflow, base_version and a note.
- Budget and variations (D-119): only when the workflow has steps with costs, ask what the person will spend and pass `budget` [{amount, unit}] to `run_workflow`; the run warns at 80% and waits before the next paid step at 100% (raise it only with their words in `person_ok`). Inputs marked as variations (copy lines, tracks) make one output per combination: the steps before the edit run once.
- At each step: where it lists what it needs and suggested models, pick the best value you can use today (price and quality on the day, not the one the source used) and report `used` {model, why}; report what it really cost in `spent`. A step that does not apply to this run: `state: "skipped"` with a note why. A phase done all at once: report `iteration: "all"` with `outputs` [{item, output}].
- Workflows 4: a step that is "another workflow" tells you to start it with `run_workflow` and `parent` {run, node}; do that run, and the step finishes by itself with its result. Inputs your person gives mid-run go in `update_run` `inputs` {key: value}; files a step makes are uploaded with the upload command and passed in `files`. A run a schedule started shows in your start_session briefing as waiting for Claude: tell your person, and do it when they say.
- Only a person marks a workflow ready, and only a person (or you, quoting their answer) answers a check. When they hand their checks to you for one run ("just this time, you check"), pass `delegate_checks: true` with their words in `person_ok`: you then pass each check against every criterion, and they can still send one back.
